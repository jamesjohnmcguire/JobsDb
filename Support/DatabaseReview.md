# Database Review and Cleanup Plan

Reviewed: 2026-11-16. This review covers the JobsDb library, database scripts, migrations, desktop startup, scraper persistence, configuration, tests, and CI. Submodules were inspected for integration context, not audited internally. This is a source review; the user's live database and email account were not opened or changed.

## Recommended Direction

Keep EF Core and migrations for now. The intended sequence is database foundation, a connected working dashboard, then email ingestion. The immediate requirement is a trustworthy, checked-in view of the current schema, with a documented way to recreate an empty database from SQL. Replacing the persistence framework would add work without resolving the existing inconsistencies by itself.

Use `SourceCode/Database/schema.sql` as the readable current schema. Generate it reproducibly from a temporary database built from committed migrations, rather than from the user's database. Keep full current `CREATE TABLE` and index definitions visible even after future migrations introduce alterations. Include the EF migration-history baseline needed for a SQL-created database to accept subsequent migrations. Exclude transient migration locks and SQLite internal implementation tables from the exported application schema. Validate the resulting bootstrap end to end.

Use `staticData.sql` only for genuine required reference data. The Tokyo search filter is editable example/user configuration, not established reference data; it should not become mandatory static data by accident.

## How the Database Works Today

1. Entity classes, nullable-reference declarations, attributes, and `*Configuration.cs` mappings collectively define EF's current model.
2. `JobsDbContext.OnModelCreating()` discovers those mappings. `Initialize()` invokes `Database.Migrate()`; the schema is persisted in a SQLite file, not merely kept in memory.
3. The default runtime file is `%LOCALAPPDATA%\JobsDb\jobsdb.db`. The design-time factory resolves to the same file.
4. The initial migration and model snapshot describe four application tables: `Jobs`, `Credentials`, `ScraperLogs`, and `SearchFilters`. EF also manages migration metadata.
5. Most repository/service tests create their schema directly from the model with `EnsureCreated()`. Context tests exercise migrations.
6. `SourceCode/Database/Schema.sql` represents a different, older design and is not used by the reviewed startup path.
7. The console has real source connectivity: `JobsDbConsole/Program.cs` calls `ScraperTester.TestTokyoDev()`, which uses `HttpClient` to fetch TokyoDev HTML, saves `tokyodev_jobs.html`, and analyzes listing candidates and selectors. This active path does not construct a database context or save job entities. Preserve this useful fetch/inspection path while joining acquisition, parsing, and persistence through shared library services.

## Itemized Findings

### Database correctness and visibility

1. **High: the existing SQL script is stale and destructive.** `SourceCode/Database/Schema.sql:1` starts by dropping `Jobs`; the script also drops and recreates `Accounts`, `Contacts`, and `Organizations`. Its `Jobs` table has `name` and `contactId`, unlike the active model's title, source identity, salary, status, and other fields. Loading it cannot recreate the application database and can destroy data. Replace it through the planned schema workflow; keep reset operations separate and explicit.

2. **High: required fields conflict with scraper output.** `Models/Job.cs` declares optional-looking text as non-nullable; the initial migration makes fields including `Requirements`, `Notes`, `RemoteType`, and `SalaryCurrency` mandatory. The active `TokyoDevScraperSelenium.ParseJobNode()` and detail fetch do not populate all of them, including `Notes` and `Requirements`. These inserts cannot satisfy the migration schema as written. Decide null versus empty-string semantics field by field, then align mappings, migrations, parsers, and tests. Do not hide missing information behind arbitrary defaults.

3. **High if enabled: the seeder violates its own schema.** `Data/JobsDbContextDbSeeder.cs:36` assigns `Source = null` to mean all sources, but `SearchFilter.Source` and the migration require a value. No call to this seeder was found in application startup. Decide whether all-source filters use nullable `Source`; then explicitly choose whether and when example filters are installed. Its existence check also depends on an editable display name, so renaming a filter can allow another copy to be seeded.

4. **Medium: there is no SQL bootstrap or schema-drift contract.** Neither CI nor the reviewed tests verifies that a SQL-created database matches migrations or can subsequently run `Initialize()`. A script with application tables but missing migration-history entries can cause EF to try creating tables again. Test both schema equivalence and migration compatibility, not just file existence.

5. **Medium: database path reporting is incomplete and tooling targets application data.** The options-based context constructor leaves `dbPath` unset, so `GetDatabasePath()` and initialization messages are inaccurate for that construction path. The factory's comment suggests a distinct design-time baseline, but its path matches the default application database. Separate path resolution from context configuration, use a connection-string builder, and require an explicit destination for database-changing developer operations.

6. **Medium: initialization and lifetime responsibilities are mixed.** Both `App.OnStartup()` and the `MainWindow` constructor call `Initialize()`. The application shares a single context across repositories and scrapers without an explicit shutdown disposal path. In `MainWindow`, later assignments rebuild constructor parameter variables after fields were assigned; they do not replace those fields. Remove redundant construction and establish one initialization owner and explicit context ownership. Assess overlapping asynchronous operations before choosing shorter context lifetimes.

7. **Medium: identity fallback undermines deduplication.** LinkedIn and TokyoDev parsers can substitute a new random identifier when source identity is missing. The unique `(Source, SourceJobId)` index cannot recognize the same listing on the next import. Require a stable source identifier or canonical source URL; reject or quarantine unidentifiable records instead of silently inventing a new identity each run.

8. **Medium: refreshes can erase known details and report misleading success.** `JobScraperBase.AddOrUpdateJobAsync()` assigns incoming optional fields over existing values, even when detail retrieval failed. Scrapers catch individual failures and can still return `Success = true`; per-job saves allow partial imports. Define how partial results, unknown values, item failures, and completion status work. Preserve user-maintained status, notes, and priority; the existing selective update already avoids overwriting these and should retain that behavior.

9. **Design decision: domain constraints and value representation are underspecified.** The migration has no explicit checks for priority 1–5, nonnegative salary values, ordered salary bounds, or valid application statuses. Salary decimals are stored as text. Indexes exist on several individual columns, but their suitability has not been measured. Document data semantics, add only agreed constraints, and evaluate query behavior before changing storage or indexes. Do not infer a need for contacts or organizations from the obsolete script alone.

10. **Medium: absence is misrepresented in repository contracts.** `GetByIdAsync()` and credential/source lookups can return null while declaring non-nullable return types. Tests explicitly expect missing records to return null. Make absence explicit consistently in interfaces, implementations, and callers.

### Test reliability

11. **High: several tests do not verify their stated guarantee.** `JobsDbContextTests.cs:122` assigns `Job badJob = TestJob`, so the duplicate-job test reuses the same tracked object instead of inserting two independent records. The duplicate-credential test leaves the second credential's required `CookieData` unset, so an exception does not prove uniqueness enforcement. The status test reads through EF without checking the raw stored string; the index test checks query results without inspecting indexes. Correct test setup and assert the specific database guarantee.

12. **Medium: persistence fixtures and schema paths need stronger isolation.** Repository tests mostly bypass migrations through `EnsureCreated()`. `BaseTestsSupport` creates mutable job objects once per fixture, and tests can alter and reuse them across cases. Create fresh entities per test. Add focused SQL-bootstrap, migration, repeat-initialization, constraint, and schema-equivalence tests. Keep model-only tests where useful, but identify them clearly. `CookieManagerTests` currently uses the application's cookie directory; inject a temporary directory before relying on the suite for isolation.

### Related cleanup

13. **High: credentials are present in source notes, and secret storage is inconsistent.** `Support/JobsDbNotes.txt` contains an API credential; its current validity was not checked. Remove it from maintained examples and rotate/revoke it through the provider if still usable. `LinkedInScraper` contains a hardcoded encryption password, configuration returns plaintext passwords from JSON, and `CredentialEncryption` derives the same key and initialization vector for repeated inputs with the same password. Establish one credential-storage policy, including cookie protection and migration of existing values. Do not copy secret values into this report or SQL fixtures.

14. **High: the dashboard is disconnected from the data and actions.** `DigitalZenWorks.JobsDb.Application/MainWindow.xaml` contains a static `FlowDocument` table of placeholder cells, with no job bindings, named dashboard controls, or action wiring. The code-behind loads jobs on `Loaded`, but the assignment to `JobsListBox.ItemsSource` and much of the interaction/error reporting are compiled out behind `FUTURE_UI`; no definition of that symbol was found in the application project or shared build properties. Startup registers scrapers, but the XAML supplies no controls to invoke their handlers. Enabling the symbol alone would reference missing controls. Replace the placeholder with actual controls and bindings, wire the supported actions, and retire the obsolete conditional scaffolding as those paths become functional. This is a near-term milestone immediately following the database foundation, ahead of email ingestion. Existing TokyoDev implementations also duplicate parsing logic, and the console already provides real HTTP retrieval and HTML inspection, although its current entry point does not persist job records.

15. **Low: repository conventions do not yet match the owner's preferences.** `.editorconfig` applies 80 columns globally, including prose and scripts. Existing code uses names such as `dbPath`, `configManager`, `ex`, `min`, and single-letter query parameters, and contains oversized lines and obsolete comments. The new root `codingStyle.md` records the requested portable rules. Plan targeted editor settings for unrestricted prose and one-line script commands. Keep existing tabs and other established settings unless deliberately changed.

16. **Low: process and dependency overhead should remain proportional.** The owner is currently the only contributor. Favor focused commits, a short validation checklist, and repeatable scripts over mandatory PR ceremony. The JobsDb library uses EF SQLite directly, while the full solution includes submodule tests and an Access Engine installation in CI. Separate core validation from dependency integration validation before deciding whether any submodule should be removed.

## Ordered Implementation Plan

1. **Establish a safe baseline.** Record the actual database location, schema, and migration history using an explicitly selected copy. Back up any data to retain before migrations or rebuilding. Repair misleading tests and isolate filesystem tests. Acceptance: focused database tests give trustworthy results and do not touch ordinary application data.
2. **Deliver schema visibility first.** Replace the obsolete script with the lowercase `schema.sql` using a Git-visible case-only rename. Add a reproducible export command/script using a temporary migrated database, a brief database README, and a direct SQLite loading example. Keep commands on one line. Acceptance: a new empty database can be created from the checked-in SQL; tables, indexes, defaults, and migration metadata match the committed migrations; EF initialization succeeds afterward. Never use this bootstrap as an existing-database upgrade or reset script.
3. **Resolve the field contract.** Inventory every column: meaning, type, nullability, default, ownership, and validation. Address missing scraper details, all-source filters, optional cookie data, salary semantics, UTC timestamps, and source identity. Add a new migration for agreed changes and refresh `schema.sql` in the same commit. Acceptance: partially populated legitimate listings save successfully; invalid required identities fail clearly; existing data remains intact.
4. **Centralize initialization and seeding.** Give startup one initialization path, correct path reporting, explicit context ownership, and observable failures. Keep editable sample filters optional. Add `staticData.sql` only if genuinely required lookup data is identified. Acceptance: repeated startup changes neither user data nor optional sample data unexpectedly, and a configured path is accurately reported.
5. **Make imports reliable.** Preserve the console's existing live-source connectivity. Expose reusable acquisition, parsing, and persistence operations from the library so the console and dashboard can use the same import path without invoking each other's entry points. Keep the useful raw-HTML inspection mode. Establish stable listing identity, explicit insert/update outcomes, preservation rules for missing incoming values, and clear partial-failure accounting. Choose a simple transaction boundary that does not encompass browser/network waits. Acceptance: importing the same input twice does not duplicate listings or erase known/user-maintained information, and failed items are visible and retryable.
6. **Add schema validation to core CI.** Compare a SQL-created temporary database with a migration-created database using schema metadata, including columns, indexes, defaults, and constraints. Exercise upgrades from the preceding baseline and detect model/migration drift. Pin the schema-generation toolchain for reproducibility. Acceptance: stale SQL, missing migrations, and broken bootstrap compatibility fail core validation without requiring browser scraping or Access integration tests.
7. **Connect a working dashboard before email ingestion.** Replace the placeholder XAML with a job list and selected-job details wired to the persistence layer. Connect search/filter, refresh, application status, notes, archive, and existing source/import actions in small working increments, reusing the shared library path established for the console and scrapers. Load persisted data on startup, refresh after imports, show empty/busy/error states, and prevent overlapping operations from using the same context concurrently. Remove the corresponding `FUTURE_UI` blocks as each path becomes live; do not add another feature flag as a substitute. Keep window code thin with a small presentation/view-model layer where it simplifies binding and testing. Acceptance: a known temporary-database job appears on launch; selection displays its details; edits survive reopening; search and archive behave correctly; a deterministic fake importer adds a job that appears after refresh; failed loads/imports are visible. Verify actual XAML bindings and event/command wiring through a WPF smoke test as well as presentation-layer tests. Validate a real source manually after the deterministic path works.
8. **Prepare email ingestion after the foundation.** Agree a small provenance design and add it through a migration plus updated SQL. Preserve original HTML and plain text, stable message/import identity, source information, receipt/import times, and processing outcome. Record parser version and structured item-level failures so a message can be reprocessed safely. One message may contain many listings, and one listing may appear in many messages; model that association instead of placing one email body on each job. Acceptance: raw inputs survive parser changes, results can be traced to their source, and reprocessing does not duplicate jobs or overwrite application tracking.
9. **Then implement email parsers and broader cleanup.** Parse preserved input into candidate listings, normalize/validate them, and persist them through the shared import path. Keep downloading email, parsing, and saving separate responsibilities. Start with local HTML/text fixtures and a simple in-process workflow; no queue service or separate service is justified yet. Address remaining credential storage, scraper duplication, and naming cleanup in focused changes; the exposed credential warrants immediate attention independently of this ordering.

## Email Design Questions to Settle During Implementation

- Is email content supplied as saved bodies/files, copied text, or fetched messages? No mailbox integration is assumed.
- Which identifier and canonical job URL remain stable across repeated digests and different sources?
- How long should original email content be retained, and how should it be protected or removed?
- Should failed or ambiguous entries be held for review, skipped, or retried? Which edits belong to the user versus the parser?

These questions do not block schema visibility or the core cleanup phases.

## Validation and Scope

The review is based on repository source and configuration. No runtime database rebuild, migration change, SQL replacement, credential rotation, or email integration has been performed. The existing `AGENTS.md` has been preserved as requested earlier. Its global line-length wording and contributor/PR assumptions should eventually be aligned with `codingStyle.md` and the single-contributor workflow.

Baseline command: `dotnet test SourceCode/JobsDbTests/JobsDbTests.csproj --verbosity quiet --logger "trx;LogFileName=database-review-baseline.trx"`. The installed SDK was 11.0.100; the projects target .NET 10.

Result: **75 passed, 0 failed, 0 skipped**. The build log contains 336 warning lines, including nullable-reference and analyzer diagnostics. The misleading uniqueness, status-storage, and index tests identified above all passed; a green baseline therefore does not establish those guarantees. No tests were added or changed during this review. The full solution, Access-dependent integration tests, live scraping, and live-database upgrades were not exercised.

The build/test log and TRX result are retained in the system temporary directory, outside the repository changes. Document changes were checked for whitespace errors; runtime implementation remains unchanged.
